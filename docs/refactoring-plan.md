# Последовательный рефакторинг Voice Memory Bot

Дата анализа: 25.10.2026. Проверенный снимок: `8b4aa00` (392 теста прошли).
База реализации: `f42f761` — мини-приложение уже удалено параллельной задачей.
Рабочий checkout `codex/voice-memory-mvp` устарел и содержит чужие изменения;
реализация ведётся в отдельном worktree поверх текущего production.

## Правила выполнения

- Каждый пункт — отдельный коммит и push в существующий `origin/main` без force.
- Проверять изменённые сценарии; при изменении общих потоков и интеграции запускать
  весь suite. Кандидат проверяется в изолированной папке серверным окружением.
- После каждого пункта с кодом выполнить guarded deploy: сверить production SHA
  и хеши под `.deploy.lock`, дождаться завершения работы, сохранить исходники,
  квитанции и SQLite, обновить только файлы релиза и проверить результат.
- Не менять пользовательские сценарии без необходимости. Сохранять полный текст,
  выбранную папку, owner isolation, версии заметок, исходники и точные Telegram ID.
- Не повторять отправку с неизвестным результатом. Удалять исходное сообщение
  только после сохранения данных и выполнения требуемой доставки.
- В журнале ниже различать реализацию, проверку и публикацию; не отмечать
  незавершённую работу выполненной.

## 1. Единый контракт поиска

Статус: опубликовано и проверено на сервере (`7103026`; 375 тестов).

**Проблема.** `Store.notes(query=..., limit=-1)` применяет Python-срез `[:-1]`,
хотя без поиска SQL трактует `LIMIT -1` как отсутствие ограничения. ИИ вызывает
этот вариант и сообщает `has_more=False`. Воспроизведение: 3 совпадения дают 2,
единственное совпадение даёт 0.

**Исправление.** Явное отсутствие ограничения через `None`, одинаковая семантика
поиска и списков, совместимость старого `-1`. Проверять параметры пагинации.
Сохранить нормализацию русского регистра/«ё» и поиск по исходному и правленому тексту.

**Готовность.** Регрессии для одного/нескольких совпадений, смещения и ограничений;
ИИ получает все совпадения, включая последнее.

## 2. Рабочая очередь и ошибочные события

Статус: опубликовано и проверено на сервере (`9498eeb`; 376 тестов).

**Проблема.** Ограничение `count(*) >= 1000` учитывает строки `failed`, а диспетчер
выбирает только `pending`. 1000 сохранённых ошибок блокируют получение новых updates.
Ошибки надо сохранять для разбора, но они не должны занимать рабочую ёмкость.

**Исправление.** Отдельные счётчики активной очереди и ошибок, явный контракт
claim/finish/fail, доступная диагностика. Не вводить слепой replay и автоматическое
удаление исходных payload: внешняя отправка могла уже выполниться.

**Готовность.** Ошибочные события сохраняются, новые принимаются; активная очередь
по-прежнему ограничена; после перезапуска восстанавливаются только допустимые состояния.

## 3. Операции над заметками вне Bot

Статус: опубликовано и проверено на сервере (`e90bdea`; 376 тестов).

**Проблема.** `Bot` наследует 7 mixin-классов; сценарии используют неявные общие
поля, архив, SQL и Telegram. Перенос и удаление особенно трудно менять изолированно.

**Исправление.** Выделять прикладные операции в сервисы с явными зависимостями:
заметки/папки, обработка медиа, экспорт. Начать с перемещения и удаления записей;
методы Bot оставить тонкими совместимыми адаптерами. Медиа/экспорт завершить в п. 10.

**Готовность.** Правила операций имеют одного владельца, вызываются UI и ИИ через
явный интерфейс; существующие проверки переноса/удаления/конкуренции проходят.

## 4. Хранилище и транзакции

Статус: явные вложенные транзакции реализованы; проверяется кандидат.

**Проблема.** SQL записей и операций разбросан между обработчиками. Вложенные
операции требуют не забыть `commit=False`, иначе можно нарушить атомарность.

**Исправление.** Выделить компоненты хранения по областям и явную единицу транзакции
с безопасным вложением; составная операция владеет commit/rollback. Убрать SQL
из извлечённых прикладных сервисов, сохранив SQLite и существующие ключи.

**Готовность.** Ошибка в середине составной операции откатывает изменение и квитанцию
вместе; вложенная операция не фиксирует незавершённую внешнюю транзакцию.

## 5. Версионированные миграции

Статус: запланировано.

**Проблема.** CREATE/ALTER выполняются в 11 модулях, включая инициализацию меню.
Изменения схемы смешаны с восстановлением прерванных заданий.

**Исправление.** Центральный последовательный запуск миграций с версией схемы.
Инициализация компонентов не меняет схему. Отдельная операция восстановления
выполняется только при старте runtime, а не при обычном открытии базы.

**Готовность.** Новая и старая базы открываются; повтор миграции безопасен;
сохраняются записи/история/очереди; диагностическое открытие не сбрасывает задания.

## 6. Единые доставка и очистка сообщений

Статус: запланировано.

**Проблема.** Текст, расшифровки, фото и ИИ отдельно управляют pending/sending/sent/unknown;
несколько путей удаления по-разному разбирают ошибки и квитанции.

**Исправление.** Общий компонент записи намерения и результата доставки, единая
классификация ошибок и политика удаления точных ID. Сохранить различия между
безопасным повтором удаления и неопределённой отправкой, а также между частями ответа.

**Готовность.** Сбой/перезапуск не вызывает автоматическую повторную отправку;
подтверждённые ID сохраняются; временная ошибка удаления остаётся повторяемой,
запрет и уже отсутствующее сообщение обрабатываются отдельно.

## 7. Типизированные состояния

Статус: запланировано.

**Проблема.** Состояния навигации и действий передаются строками и произвольными
словарями, дублируются в action, bottom_menus и folder_views. Типы медиа/ошибок неоднородны.

**Исправление.** Явные типы экранов, действий и жизненного цикла; отдельный разбор
сериализованных значений и переходы. Сохранить формат существующих callback и
сохранённых экранов через адаптеры, а также происхождение старых web-записей.

**Готовность.** Назад/Главная/Отмена, устаревшие кнопки, подтверждения и restart
сохраняют прежнее поведение; новые сервисы используют типы вместо неявных строк.

## 8. Долгие операции и рабочие циклы

Статус: запланировано.

**Проблема.** Долгий UI-обработчик задерживает диспетчер; любой view_rendering
приостанавливает выбор заданий обоих worker для всех пользователей.

**Исправление.** Планирование с сохранением порядка для одного пользователя,
ограничение одновременно активной работы и локальные блокировки. Не менять
сохранённую SQLite-очередь на ненадёжную очередь только в памяти.

**Готовность.** Долгая операция одного пользователя не блокирует независимого;
для одного пользователя команды/заметки не меняют порядок; shutdown сохраняет
незавершённую работу; защита несохранённых исходников действует.

## 9. Контекст ИИ и запуск провайдера

Статус: запланировано.

**Проблема.** AssistantEngine собирает историю, сообщения, записи, права и результаты
действий одновременно; полный контекст может повторяться. CodexRouter совмещает
запуск процесса и историческую классификацию папок.

**Исправление.** Отдельный ContextBuilder с явной полнотой и измерением размера;
сохранять полный выбранный текст/историю, большие выборки предоставлять управляемо.
Общий runner запуска процесса с теми же ограничениями окружения, таймаутом и отменой.

**Готовность.** Полный контекст и фото не теряются, права проверяются как прежде;
повтор шага использует сохранённый результат; запуск и отмена имеют один контракт.

## 10. Медиа, производные файлы и экспорт

Статус: запланировано.

**Проблема.** Archive управляет исходниками, текстовыми представлениями, удалением,
документами и ZIP. Обработка медиа остаётся внутри Bot.

**Исправление.** Разделить хранение исходников, материализацию текстов, обработку
медиа и сборку экспорта. Экспорт: снимок → документы/файлы → ZIP-части → проверка.
Сохранить потоковое копирование, хеши, полный текст и отмену без удаления рабочего каталога раньше времени.

**Готовность.** Все форматы и старые web-исходники экспортируются, повреждённый файл
не даёт частичную выгрузку; сбои обработки не уничтожают оригинал.

Статус: не требуется после `f42f761`.

В исходном анализе предлагалось разделить app.js на API/состояние/запись/загрузки/UI.
Мини-приложение удалено параллельной задачей по решению пользователя. Восстанавливать

## 12. Тестовая инфраструктура и старые проверки

Статус: запланировано.

**Проблема.** Тесты импортируют фикстуры друг из друга; check_pipeline ожидает
отменённую автоматическую маршрутизацию по тексту; общий Ruff сообщает две ошибки импортов.

**Исправление.** Общие фикстуры/помощники в выделенном тестовом модуле и conftest;
актуализировать проверку пути ASR → сохранение в выбранной папке → экспорт.
Не вызывать платные/внешние проверки при обычном pytest.

**Готовность.** Тестовые модули не служат библиотекой друг для друга; smoke проверяет
текущий контракт; весь suite и Ruff чистые; тесты проверяют важное поведение.

## 13. Диагностика и воспроизводимый выпуск

Статус: запланировано.

**Проблема.** Данные о зависших заданиях ограничены; процедура релиза существует
в правилах и отдельных временных скриптах. HTTP healthz удалён вместе с mini app.

**Исправление.** Безопасная read-only CLI-диагностика очередей/ошибок/активности и
версионированный guarded release tool с проверкой базы, manifests, резервной копией,
ожиданием idle, обновлением, проверкой runtime и сохранностью архива. Без секретов
и текстов сообщений в выводе. Не возвращать удалённый HTTP-сервис.

**Готовность.** Смена production во время подготовки останавливает выкладку до
замены файлов; неуспешный запуск откатывает код, не откатывая новые пользовательские
данные; опубликованный SHA и результат проверок записаны в квитанции.

## Журнал реализации

- План записан до изменений кода отдельным коммитом `64e64ea`.
- Пункт 1: `None` и старый `-1` возвращают все совпадения; одинаковая пагинация
  для поиска и списка. Добавлены две регрессии (хранилище и ИИ). Целевая проверка:
  4 теста прошли; Ruff изменённых файлов чистый.
- Пункт 1 опубликован: `7103026`, 375 тестов, manifest/SQLite/архив/запуск проверены.
- Пункт 2: операции очереди выделены в `UpdateQueue`; лимит считает только pending
  и processing, размер входящего пакета ограничен оставшейся ёмкостью. Failed payload
  сохраняется без автоматического повтора.
- Пункт 2 опубликован: `9498eeb`, 376 тестов; рабочая очередь и архив сохранены.
- Пункт 3: UI и ИИ вызывают NoteService; Bot делегирует перенос и очистку,
  MessageStore владеет чтением и удалением точных квитанций. Проверены переносы,
  удаления, AI batch, блокировки и старые архивы: 50 тестов; Ruff src чистый.
- Пункт 3 опубликован: `e90bdea`, 376 тестов; архив и запуск проверены.
- Пункт 4: все операции используют одну единицу транзакции с savepoint для
  вложенных вызовов. Удалены параметры commit=False и ручные BEGIN в сценариях.
  Регрессии проверяют общий rollback записи/папки/квитанции и откат отдельного
  вложенного шага без потери соседних изменений. В транзакциях нет await.
