# Проверка и выпуск Voice Memory Bot

## Диагностика без изменения данных

```bash
PYTHONPATH=src .venv/bin/python -m voice_memory_bot.cli diagnose \
  --database data/archive.sqlite3
```

Команда открывает существующую SQLite с `mode=ro`, без конфига, миграций,
восстановления заданий и внешних API. Показывает целостность базы, состояния
очередей, неопределённую доставку, ожидающую очистку и возраст ожидающих записей/ИИ.
Тексты, токены, payload и содержимое ошибок не выводятся. Возраст считается от
создания записи, а не от последней попытки. В updates дата постановки не хранится:
для неё возраст явно неизвестен. Это снимок состояния, а не проверка доступности Telegram.

Код завершения: `0` — известных проблем нет, `1` — требуется внимание либо проверка
не выполнена. Ошибки доставки `unknown` нельзя повторять автоматически: Telegram
мог принять сообщение до обрыва ответа. Failed updates сохраняются для разбора.

## Воспроизводимый выпуск

Цель зафиксирована в `scripts/release.py`: `my-server`,
`/home/tony/Desktop/_code/voice_memory_bot`, пользовательская служба
`voice-memory-bot.service`. Инструмент использует существующий SSH config и origin.
На сервере требуется Python 3.12+ и подготовленная `.venv` с dev-зависимостями.

Начинай с чистого checkout поверх SHA из серверного `release.json`; сначала
сверь `origin/main` и интегрируй параллельные изменения. Зафиксируй свою задачу.
Затем из этого checkout:

```bash
release_sha=$(git rev-parse HEAD)
base_sha=$(ssh -F "$HOME/.ssh/config" -o BatchMode=yes my-server \
  cat /home/tony/Desktop/_code/voice_memory_bot/release.json \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["commit"])')
python3 scripts/release.py prepare "$release_sha" "$base_sha"
git fetch origin
git push origin HEAD:main
python3 scripts/release.py deploy "$release_sha" "$base_sha"
```

`prepare` требует, чтобы production SHA был предком нового коммита, собирает
`git archive`, вычисляет SHA-256 файлов и загружает отдельный кандидат. Его полный
pytest, Ruff и миграция приватной копии production SQLite должны пройти. Только
после этого создаётся `validation.json`, связанный с SHA и manifest. Кандидат одного
SHA не перезаписывается; исправленный код должен получить новый коммит.

`deploy` требует совпадения кандидата с текущим `origin/main`. Серверный guard:

1. Берёт `.deploy.lock`, проверяет базовый SHA, хеши, квитанцию проверок и пути.
   Конфиги, data, служебные каталоги и symlink в исходниках запрещены.
2. Сохраняет исходники и квитанции; ждёт свободную очередь. При истечении 180 секунд
   останавливается без перезапуска бота.
3. Повторно сверяет production, останавливает только эту службу и проверяет,
   что между ожиданием и остановкой не появились задания.
4. Сохраняет согласованную SQLite backup и контрольный снимок архива; заменяет
   только файлы manifest. Конфиги, оригиналы и база не копируются из кандидата.
5. Проверяет неизменность данных во время замены, запускает службу и проверяет
   реальный старт Telegram, `active/running`, отсутствие новых предупреждений,
   manifest, целостность SQLite и сохранность записей.

Если старт/проверка не проходит, guard восстанавливает прежний код и запускает
службу. SQLite и медиа не откатываются: новые пользовательские данные сохраняются.
Миграции поэтому должны оставаться совместимыми с предыдущим кодом; разрушительные
изменения схемы требуют отдельного плана миграции и отката.

Результат — `deploy-receipt.json` и резервная копия в `.deploy-backups/`.
`concurrent_source_change` означает: заново получить production SHA, интегрировать
изменения и проверить нового кандидата. При `untracked_source_conflict` сначала
разбери конкретный конфликт; чужие файлы автоматически не заменяются.
